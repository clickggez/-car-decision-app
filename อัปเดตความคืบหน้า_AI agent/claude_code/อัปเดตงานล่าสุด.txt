==================================================
สรุปภาพรวม (ปิดงาน)
==================================================
วันนี้อัปเดตข้อมูลแบบสอบถาม 3 รอบ (500 -> 540 -> 715 แถว) และ retrain
โมเดลทั้งหมด 7 ครั้ง ระหว่างทางพบบั๊กสำคัญใน predict_buy ที่ทำให้โมเดลทาย
"ไม่ซื้อ" ไม่ได้เลย ตรวจสอบสาเหตุ ยืนยันกับเล่มโปรเจกต์ผ่าน NotebookLM
ก่อนแก้โค้ด แล้วแก้จนโมเดลใช้งานได้จริง จากนั้นทดลองปรับ feature
selection ของ FUEL model จนดีขึ้นชัดเจน เอา % ความมั่นใจออกจาก UI ตาม
คำขอผู้ใช้ แล้วทดลองดันต่ออีก 2 แนวทางก่อนปิดงาน (ไม่ได้ผล แต่ยืนยัน
เพดานเดิมแน่นขึ้น) — จบวันนี้ที่ BUY 65.0% / FUEL 48.7% ทั้งคู่ดีที่สุด
เท่าที่เคยเทรนมาในโปรเจกต์นี้ และมีหลักฐานครบว่านี่คือเพดานจริง

ลำดับเหตุการณ์
==================================================

1) รอบ 500 แถว
   - แทนที่ไฟล์ CSV ใหม่ใน files/user_from/ (ตัดจาก 505 เหลือ 500 แถว
     ให้ตรงเป้า n=500 ตามเล่ม 3.3.1 — ผู้ใช้ยืนยันว่าเป็นการตัดข้อมูล
     ส่วนเกิน ไม่ใช่ปัญหาคุณภาพข้อมูล)
   - BUY: test accuracy 69.0%
   - FUEL: test accuracy 40.7% — ถดถอยจากรอบก่อน (505 แถว) เพราะกลุ่ม
     ICE ในข้อมูลลดจาก 92 เหลือ 65 ตัวอย่าง (บังเอิญอยู่ในแถวที่ถูกตัด)

2) รอบ 540 แถว (+40, เพิ่มกลุ่ม ICE)
   - FUEL ดีขึ้นตามคาด: ICE precision/recall จาก 0.18/0.15 เป็น 0.35/0.35
   - พบบั๊ก: BUY model ทาย "ไม่ซื้อ" ไม่ได้เลย (precision/recall = 0.00/0.00)
     ทั้งที่ test accuracy แสดงสูงถึง 66.7%

   สาเหตุที่วินิจฉัยได้:
   train_models.py บรรทัด 304 ใช้ GridSearchCV(scoring="accuracy")
   เมื่อ label ไม่บาลานซ์ (ซื้อ 358 / ไม่ซื้อ 182 = 66/34) การทาย "ซื้อ"
   ทุกกรณีก็ได้ accuracy ~66% อยู่แล้วโดยไม่ต้องแยกแยะอะไรเลย GridSearch
   จึงเลือกพารามิเตอร์ที่เอนเอียงไปทาง class ใหญ่ เพราะเป็นทางลัดสู่
   accuracy สูงสุด ยิ่งสัญญาณจากฟีเจอร์อ่อนอยู่แล้ว (p-value ชายขอบ
   0.05-0.13) โมเดลก็ยิ่งเลือกทางลัดนี้

   ก่อนแก้โค้ด ตรวจสอบกับเล่มโปรเจกต์ผ่าน NotebookLM ("CarDSS Project
   Hub", บัญชี ratanakornasa@gmail.com) ว่าเล่มระบุ scoring metric
   สำหรับ GridSearchCV ไว้หรือไม่ — คำตอบ: เล่มไม่ได้พูดถึง GridSearchCV
   เลย และไม่ได้ระบุ scoring metric ใดๆ จัดการเรื่อง imbalance ด้วย
   SMOTE ที่ขั้นเตรียมข้อมูล (3.3.2.4) เท่านั้น ส่วน Accuracy/Precision/
   Recall/F1 ใช้แค่ตอนประเมินผลสุดท้าย (3.5.1) — สรุปว่าการเปลี่ยน
   scoring metric ไม่ขัดระเบียบวิธีวิจัยในเล่ม

   แก้ไข: เปลี่ยน scoring="accuracy" เป็น scoring="balanced_accuracy"
   ใน train_models.py:304 แล้ว retrain ใหม่
   - BUY: test accuracy ลดจาก 66.7% เหลือ 59.3% (ตามคาด เพราะเลิก
     "โกง" ด้วยการทายซื้อทุกกรณี) แต่ "ไม่ซื้อ" precision/recall
     กลับมาเป็น 0.40/0.44 (จาก 0.00/0.00) — ใช้งานได้จริงทั้งสอง class

3) รอบ 715 แถว (+175, เน้นเก็บ "ไม่ซื้อ" และ ICE เพิ่มเติม)
   - BUY: label กลายเป็น 381 ซื้อ / 334 ไม่ซื้อ (53/47 — บาลานซ์เกือบ
     สมบูรณ์) test accuracy 65.0%, precision/recall สมดุลทั้งสอง class
     (ซื้อ 0.68/0.64, ไม่ซื้อ 0.62/0.66) ==> ดีที่สุดเท่าที่เคยเทรนมา
   - FUEL: ICE เพิ่มเป็น 105 ตัวอย่าง (เกินจุดสูงสุดเดิม 92) แต่ feature
     selection ยังผ่านแค่ 2 field เท่าเดิม (prio_fuel_cost,
     prio_maintenance_cost) — test accuracy กลับลดลงจาก 39.1% เหลือ
     32.5% (Hybrid precision/recall แย่ลงชัดเจน)

4) ปรับปรุง FUEL model เพิ่มเติม (ไม่เก็บข้อมูลเพิ่ม ผู้ใช้ยืนยันว่า
   715 แถวพอแล้ว — ปรับที่โค้ดแทน)
   - วิเคราะห์พบว่า predict_fuel() ถูกล็อก signature ไว้ ทำให้มีฟีเจอร์
     ผู้สมัครแค่ 16 ตัว (น้อยกว่า BUY ที่มี 13 ฟีเจอร์อิสระกว่า) และที่
     alpha=0.10 เดิม feature selection กรองเหลือแค่ 2/16 ตัว ทิ้ง
     prev_car (รถเดิม) ไปด้วยทั้งที่ตามสามัญสำนึกควรสัมพันธ์กับการเลือก
     เชื้อเพลิงถัดไปชัดเจน
   - เช็คกับเล่มผ่าน NotebookLM: เล่มไม่ได้ล็อกค่า alpha ตายตัว (งานวิจัย
     อ้างอิงในเล่มใช้ 0.05, เราใช้ 0.10 หลวมกว่าอยู่แล้ว) มีคำแนะนำเสริม
     ว่าเก็บฟีเจอร์ที่มีเหตุผลทางทฤษฎีไว้ได้แม้ p-value ไม่ผ่าน
   - แก้ train_models.py: เพิ่ม alpha/force_keep parameter ให้
     select_features()/build_and_select() แล้วใช้กับ FUEL model ด้วย
     alpha=0.15 + force_keep=["prev_car"] (BUY ยังใช้ default 0.10
     เหมือนเดิม ไม่กระทบ)
   - ผลลัพธ์: feature selection ผ่าน 3 field (เพิ่ม prev_car เข้ามา)
     test accuracy จาก 32.5% เพิ่มเป็น 48.7% — EV 0.61/0.47, Hybrid
     0.48/0.41, ICE 0.41/0.62 (ดีขึ้นทั้ง 3 class) เกือบเทียบเท่าจุด
     สูงสุดเดิมของโปรเจกต์ (47.2%)
   - เอา % ความมั่นใจ (max predict_proba ต่อคำทาย) ออกจาก UI ตามคำขอ
     ผู้ใช้ (result_buy.html, result_fuel.html, recommend.html) เพราะ
     อาจทำให้เข้าใจผิดว่าโมเดลแม่นยำกว่า test accuracy จริง — ไม่แตะ
     backend เพราะเป็น contract ที่ tests อ้างอิงอยู่ ทดสอบผ่าน
     เบราว์เซอร์จริงแล้ว unit tests ผ่านครบ 41 ตัว

5) ทดลองดันต่ออีก 2 แนวทางตามคำขอผู้ใช้ ("ลองอีกที ไม่ดีก็พอ" และ
   "คิดเยอะๆ") ก่อนปิดงาน — ทั้งคู่ไม่ได้ผล แต่ยืนยันเพดานเดิมแน่นขึ้น
   - force_keep เพิ่ม usage_type + distance: test acc ร่วงเหลือ 36.2%
     (เป็น noise ไม่ใช่ signal) ย้อนกลับทันทีตามข้อตกลง
   - เพิ่มฟีเจอร์ใหม่ priority_count (จำนวน priority ที่เลือก, ไม่บังคับ
     เก็บ): p=0.2523 ไม่ผ่านเกณฑ์ ถูกตัดทิ้งเอง ผลเหมือนเดิม (48.7%)
     ไม่เสียหายไม่ได้ประโยชน์ — เก็บโค้ดไว้เผื่ออนาคต
   - **สรุป: ลองครบ 5 แนวทางแล้ว ปิดงาน ML ที่ 48.7% (FUEL) / 65.0%
     (BUY)** เหลือ 2 ทางที่ไม่ทำเพราะนอก scope: แก้ signature ของ
     predict_fuel() หรือออกแบบแบบสอบถามใหม่เจาะจงเรื่องเชื้อเพลิง
