# สถาปัตยกรรมโปรเจกต์ (Project Architecture)

**ชื่อโปรเจกต์:** Car-Decision-App (CarDSS)
**สถานะปัจจุบัน:** เกือบสมบูรณ์ (High Maturity Phase)

## 🏗️ Tech Stack & Core Logic

- **Backend:** Flask (`app.py`), การจัดการ Sessions
- **Deployment / Hosting:** PythonAnywhere (รันโค้ดผ่าน GitHub Clone: `https://r4tt4.pythonanywhere.com`)
- **Database:** Firebase (Auth/Firestore) พร้อมระบบ Local Mode สำรอง (JSON)
- **Data Source:** `data/cars.json` (แบ่งหมวดหมู่เป็น EV, Hybrid, ICE)
- **AI Models:** Scikit-learn & TensorFlow (เก็บไว้ใน `models/`)
  - `predict_buy`: ทำนายว่าควร "ซื้อ" หรือ "ไม่ซื้อ"
  - `predict_fuel`: แนะนำประเภทเชื้อเพลิง (EV, Hybrid, ICE)

## ✅ กฎของระบบ (DO)

1. Logic หลักมีความเสถียรแล้ว ให้โฟกัสที่:
   - การปรับปรุงประสิทธิภาพ (Optimization)
   - การแก้ไขบั๊ก (Bug fixing)
   - การจัดการกรณีพิเศษ (Edge-case handling)
2. ตรวจสอบให้แน่ใจเสมอว่า Local Mode (JSON) ทำงานได้ไหลลื่นกรณี Firebase ไม่เชื่อมต่อ
3. เขียน unit test สำหรับ edge case ใหม่ทุกครั้งที่เจอ

## ❌ ข้อห้ามเด็ดขาด (DO NOT)

1. ห้ามเปลี่ยน signature ของ `predict_buy()` และ `predict_fuel()`
2. ห้ามเปลี่ยน schema ของ `data/cars.json` (field names, types, categories)
3. ห้าม retrain หรือเปลี่ยนไฟล์ model ใน `models/` โดยไม่ได้รับคำสั่ง
4. ห้ามแก้ไข Firebase Auth flow ที่ใช้งานได้แล้ว
5. ห้ามเพิ่ม dependency ใหม่โดยไม่ update `requirements.txt` และแจ้งใน handoff

### ⚠️ ไฟล์ `.ps1` ที่มีภาษาไทย **ต้องบันทึกเป็น UTF-8 ที่มี BOM** (พบ 2026-08-08)

Windows PowerShell 5.1 อ่านไฟล์ `.ps1` เป็น ANSI codepage เมื่อ**ไม่มี BOM** คอมเมนต์ภาษาไทย
จะกลายเป็น mojibake และอักขระอย่าง `—` `“` `"` ทำให้ตัว parser พังทั้งไฟล์
(อาการที่เจอ: `Unexpected token '}'`, `The string is missing the terminator`)

⚠️ **เครื่องมือเขียนไฟล์ของ AI agent ส่วนใหญ่บันทึกเป็น UTF-8 ไม่มี BOM** ต้องแปลงหลังเขียนทุกครั้ง

```powershell
$p = "path\to\script.ps1"
$t = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
[System.IO.File]::WriteAllText($p, $t, [System.Text.UTF8Encoding]::new($true))
# ตรวจ: 3 ไบต์แรกต้องเป็น 239,187,191
```

ตรวจไวยากรณ์ก่อนรันงานยาว:
```powershell
$e=$null; [void][System.Management.Automation.Language.Parser]::ParseFile($p,[ref]$null,[ref]$e); $e
```

### 🔴 Construct Mismatch ของ label `predict_buy` (พบ 2026-08-02) — ต้นตอที่แท้จริงของทุกความผิดปกติ

**สรุป: label ที่ใช้เทรน `predict_buy` มาตลอดทั้งโปรเจกต์ ไม่ได้วัด "จะซื้อรถหรือไม่"**

ข้อความจริงของคำถามที่ใช้เป็น label (คอลัมน์ 20 ของ CSV):
> "4. ท่านมีแนวโน้มจะซื้อรถยนต์**ตามประเภทเชื้อเพลิงที่ท่านสนใจ**หรือไม่"
> ตัวเลือก: "มีแนวโน้มที่จะซื้อ" (292) / "ยังไม่มีแนวโน้มที่จะซื้อ" (208)

วลี "ตามประเภทเชื้อเพลิงที่ท่านสนใจ" เปลี่ยน construct ทั้งหมด — คำถามนี้ไม่ได้ถาม *Will you buy a car?*
แต่ถาม *Will you buy the fuel type you prefer?* ซึ่งเป็น **Conditional purchase of preferred fuel type**
(หรือ purchase feasibility) ไม่ใช่ **Purchase Intention** ตามกรอบ TPB

**อธิบายความผิดปกติที่ค้างคามานานได้ทั้งหมด:**

| ปรากฏการณ์ | เคยเข้าใจว่า | คำอธิบายที่ถูกต้อง |
|---|---|---|
| คนตอบ "ตั้งใจซื้อ 7/7" (คอลัมน์ 44) แต่ label = "ไม่มีแนวโน้มซื้อ" 54.5% (p=0.2068) | ข้อมูลเสีย / คนตอบมั่ว / scale กลับด้าน | **วัดคนละ construct** — ตั้งใจซื้อรถจริง แต่จะไม่ซื้อชนิดที่ตัวเองชอบ (เช่น ชอบ EV แต่ซื้อ ICE เพราะงบ/ไม่มีที่ชาร์จ) |
| `charging_access` p=0.0001 กับ BUY แต่ p=0.950 กับ FUEL | ขัดกับทฤษฎี EV adoption | **สอดคล้องสมบูรณ์** — มีที่ชาร์จ = ซื้อตามชนิดที่ชอบได้จริง ส่วน "ชอบชนิดไหน" เป็นคนละเรื่อง |

**ผลกระทบต่องาน:** ชื่อโปรเจกต์คือ *Car Purchase Decision Support System* แต่โมเดลแรกไม่ได้เรียน
*Purchase* — มันเรียน *Conditional purchase of preferred fuel* ซึ่งเป็นคนละ outcome
→ **Research question ของโมเดล BUY ต้องปรับถ้อยคำให้ตรงกับสิ่งที่วัดจริง** (ไม่ได้แปลว่างานใช้ไม่ได้)

**⛔ ห้ามเปลี่ยนไปใช้คอลัมน์ 44 (เจตนาซื้อ 1-7) เป็น label แทน** — เหตุผล 2 ข้อ:
1. **Outcome switching** — เปลี่ยน endpoint หลังเห็นว่าผลเดิมไม่สวย เป็นสิ่งที่ reviewer/กรรมการจับได้ทันที
2. **Construct leakage** — ฟีเจอร์มี `attitude`/`subjective_norm`/`pbc_financial` ซึ่งตาม TPB ออกแบบมา
   เพื่ออธิบาย intention อยู่แล้ว ถ้าใช้ intention เป็น label ด้วย accuracy จะสูงขึ้นแบบไม่มีความหมาย

ถ้าจะทำ ต้องแยกเป็น **Study 2 / Additional analysis** ให้ชัดเจน และควรใช้ ordinal classification (1-7)
แทนการ binarize ที่ threshold ตามใจ (5 หรือ 4 หรือ 6 — reviewer จะถามว่าทำไมเลือกค่านั้น)

**ข้อความที่แนะนำให้เขียนลงเล่ม (บทอภิปราย):**
> "ระหว่างการวิเคราะห์ พบว่าตัวแปรตามที่ใช้ในโมเดล BUY มีความหมายเชิงแนวคิดแตกต่างจาก Purchase Intention
> ตามกรอบ TPB โดยสะท้อน 'แนวโน้มที่จะซื้อรถยนต์ตามประเภทเชื้อเพลิงที่สนใจ' มากกว่าความตั้งใจซื้อรถยนต์
> โดยทั่วไป ผลดังกล่าวอธิบายได้ว่าทำไมตัวแปร Purchase Intention จึงไม่สัมพันธ์กับตัวแปรตาม และทำไม
> ความพร้อมด้านโครงสร้างพื้นฐานการชาร์จจึงมีความสัมพันธ์กับตัวแปรตามดังกล่าว"

### ⚠️ ข้อบกพร่องของแบบสอบถาม — โน้ตสำหรับผู้วิเคราะห์หลุดไปให้ผู้ตอบเห็น (พบ 2026-08-02)

คำถาม NEP ข้อที่ 5 (คอลัมน์ 58) ที่แสดงในฟอร์มจริงมีข้อความกำกับติดไปด้วย:
> "มนุษย์มีสิทธิที่จะปรับเปลี่ยนสิ่งแวดล้อมทางธรรมชาติให้ตรงกับความต้องการของตน
> **[ข้อนี้เป็น reverse-worded ให้กลับคะแนนตอนวิเคราะห์]**"

วงเล็บนั้นควรเป็นโน้ตภายในสำหรับผู้วิเคราะห์ ไม่ควรแสดงต่อผู้ตอบ

**ผลที่ตามมา: ใช้เป็น attention check ไม่ได้**
- correlation ระหว่างคะแนนดิบของข้อ reverse กับค่าเฉลี่ย 4 ข้อ forward = **+0.049** (ควรเป็นลบชัดเจน)
- ค่าเฉลี่ย forward 4.45 vs reverse 4.46 → ผู้ตอบเห็นด้วยไปทางเดียวกันหมด = **acquiescence bias ทั้งกลุ่ม**
- ถ้าใช้เกณฑ์นี้คัด จะคัดออก 278/500 คน (55.6%) ซึ่ง**ไม่ควรใช้เป็นผลหลัก** (คัดครึ่งกลุ่มตัวอย่าง + ตัวเกณฑ์เองมีข้อบกพร่อง)
- **แต่ sensitivity analysis มีค่า:** คัดแล้ว BUY 68.5%→67.4%, FUEL 41.3%→44.8% = **ผลไม่เปลี่ยนอย่างมีนัยสำคัญ**
  → เป็นหลักฐานว่าตัวเลขที่รายงานไม่ได้เกิดจากผู้ตอบไม่ตั้งใจ (ทำให้ข้อสรุปแข็งขึ้น ไม่ใช่อ่อนลง)
- Straight-lining = 0 คน, Longstring ≥14 = 0 คน (สูงสุดที่พบ 13) → ไม่มีหลักฐานการตอบมั่วแบบอื่น

**ผลลัพธ์ที่เป็นหลักฐานหนักแน่นที่สุดเท่าที่มี:** **ไม่มีฟีเจอร์ตัวไหนผ่าน permutation threshold เลยสักตัว ทั้ง BUY และ FUEL**

- FUEL: threshold=0.0768, ฟีเจอร์ที่คะแนนสูงสุด (`prio_fuel_cost`=0.0675, `tech_cost_balance`=0.0632) ยังต่ำกว่า threshold

พูดง่ายๆ คือแม้แต่ฟีเจอร์ที่ "ดูดีที่สุด" ในชุดข้อมูล ก็ยังมีคะแนนความสัมพันธ์กับ label ที่อยู่ในช่วงที่คาดหวังได้จากการสุ่ม label ล้วนๆ (noise) — นี่คือหลักฐานเชิงสถิติที่เข้มงวดที่สุด (distribution-free, ผ่าน permutation test) ที่ยืนยันว่า **ไม่มีฟีเจอร์ตัวใดในแบบสอบถามที่มีสัญญาณจริงเกินกว่าโอกาสสุ่มเลย** สอดคล้องและตอกย้ำ Known Issue "Data Signal" ที่พบด้วย Chi-square/ANOVA — ไม่ใช่เพราะเลือกใช้เทคนิคผิด แต่เพราะสัญญาณไม่มีอยู่จริงในการวัดแบบไหนก็ตาม (ผลลัพธ์ตัวเลขโมเดลไม่เปลี่ยนจากก่อนหน้า เพราะ MI fallback กลับไปใช้ฟีเจอร์ทั้งหมดเหมือน 'all' set อยู่แล้วเมื่อไม่มีอะไรผ่านเกณฑ์)

1. **ไม่มี whitelist ของค่า select** — endpoint ยอมรับทุก string ที่ไม่ใช่ empty เช่น `gender="alien"`, `budget="999999999999"` ผ่าน validation แล้ว pass-through ไปโมเดล
   - **ผลกระทบ:** เมื่อ `USE_MOCK = False` โมเดลจริงอาจ crash เพราะ encode feature ไม่ได้ หรือทำนายผิด
   - **แนะนำ:** เพิ่ม dict whitelist ต่อ field ใน `api_predict_buy` หรือสร้าง validator ส่วนกลาง

2. **ไม่ตรวจค่าติดลบ** — เช่น `children="-1"`, `income="-50000"` ผ่าน validation ปัจจุบัน
   - **ผลกระทบ:** เหมือนข้อ 1 — UI ส่งไม่ได้ แต่ raw POST ส่งได้

3. **Whitespace-only bypass** — `if not v` ใน `app.py:405` catch เฉพาะ empty string ไม่ catch `"   "` (space-only)
   - **แนะนำ:** เปลี่ยนเป็น `if not v.strip()`

4. **ไม่มี sanitization ต่อ XSS/SQL payload** — ค่าอย่าง `<script>alert(1)</script>` หรือ `'; DROP TABLE --` ผ่านไปถึง Firebase/session
   - **ผลกระทบ:** หาก render input_data ใน template โดยไม่ escape อาจเกิด XSS (Jinja2 auto-escape ช่วยได้บางส่วน แต่ไม่ป้องกัน Firestore)
